# jdanoff search

Локальный поиск по собственным текстовым документам на **C++20**: собственный инвертированный индекс, ранжирование **BM25**, HTTP API на **userver** и минималистичный веб-интерфейс.

Загрузи `.txt`, введи запрос и получи документы с оценкой релевантности и коротким отрывком. Документы сохраняются на диске, индекс восстанавливается при запуске.

**v1 реализована.** Следующий этап — позиционный индекс и сниппеты вокруг совпадений: [задача v2](https://github.com/mialzh/local-search/issues/7).

## Возможности

- Загрузка UTF-8 документов через браузер или HTTP API.
- Поиск по Unicode-токенам без учёта регистра.
- BM25 с суммированием вкладов уникальных слов запроса.
- Детерминированная выдача: score ↓, при равенстве — ID ↑.
- Сниппет из первых 200 кодовых точек исходного текста.
- Сохранение документов в JSON и восстановление индекса после перезапуска.
- Веб-интерфейс **jdanoff search** без отдельной сборки фронта.
- Юнит-тесты ядра, HTTP smoke-тест и тесты клиента API.

## Как это устроено

| Слой | Ответственность |
|---|---|
| `web/` | Интерфейс загрузки и поиска; HTML, CSS, JavaScript |
| `src/http/` | Валидация HTTP-запросов, JSON-ответы и ошибки |
| `src/components/` | Интеграция движка с userver, восстановление и синхронизация |
| `src/search/` | Обработка текста, инвертированный индекс, BM25 и поиск |
| `src/storage/` | Сохранение и чтение документов |

**Добавление:** исходный текст → нормализованные токены → сохранение документа → обновление индекса.

**Поиск:** запрос → уникальные нормализованные токены → списки документов → сумма BM25 → сортировка → результаты.

Индекс хранит для каждого слова список `Posting { document_id, frequency }`, а также длины документов и статистику коллекции. Запрос совпадает с документом, если найдено **хотя бы одно** его слово. Порядок слов не учитывается; повтор слова в запросе не увеличивает оценку.

Ядро не зависит от HTTP-слоя и собирается отдельно. В текущей реализации операции движка защищены одним mutex; файловые операции выполняются через отдельный task processor userver.

## Стек

| Компонент | Технология |
|---|---|
| Ядро | C++20 |
| HTTP-сервер | userver |
| Unicode | ICU |
| Хранение | JSON-файлы, nlohmann/json |
| Сборка | CMake ≥ 3.20 |
| Юнит-тесты | Catch2 3 |
| HTTP-тесты | Python 3 |
| Фронт | HTML, CSS, JavaScript modules |

CMake ожидает установленные зависимости через `find_package`: ICU, nlohmann_json, Catch2 3 для тестов и userver для сервера. Автоматическая загрузка зависимостей в текущем CMake не настроена.

## Запуск сервера и сайта

Команды выполняются из корня репозитория. Для Windows используется Ubuntu в WSL2 с Docker.

Открыть окружение с userver:

```bash
docker run --rm -it \
  -p 127.0.0.1:8080:8080 \
  -v "${PWD}:/work" \
  -w /work \
  --entrypoint bash \
  ghcr.io/userver-framework/ubuntu-22.04-userver:latest
```

Внутри контейнера:

```bash
cmake -S . -B build-server -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_SERVER=ON \
  -DBUILD_TESTING=OFF

cmake --build build-server --parallel 2
./build-server/local_search -c configs/static_config.yaml
```

В окружении должны быть доступны ICU и CMake-пакет nlohmann_json. Если CMake не находит их, зависимости нужно установить или указать путь к ним.

Открыть **[http://localhost:8080](http://localhost:8080)**. Сервер сам отдаёт `web/`; npm и отдельный dev-сервер не нужны.

Проверить доступность:

```bash
curl http://127.0.0.1:8080/health
```

Ответ: `ok`.

### Конфигурация

Настройки находятся в [configs/static_config.yaml](configs/static_config.yaml):

| Настройка | Текущее значение |
|---|---|
| Адрес внутри контейнера | `0.0.0.0` |
| Порт | `8080` |
| Каталог данных | `./data` |
| Статические файлы | `./web` |

Сервер нужно запускать из корня репозитория: относительные пути считаются от рабочего каталога. Docker-команда публикует порт только на локальном интерфейсе хоста. Каталог проекта смонтирован в контейнер, поэтому данные сохраняются после его остановки.

## API

Полный контракт: [contracts/openapi.yaml](contracts/openapi.yaml).

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/health` | Проверка доступности |
| `POST` | `/documents` | Загрузка одного документа |
| `GET` | `/search?q=…&limit=10` | Поиск документов |

### Загрузка

```bash
printf '%s' 'Умные указатели управляют памятью.' > /tmp/pointers.txt
curl -F 'file=@/tmp/pointers.txt' http://127.0.0.1:8080/documents
```

Ответ `201 Created`:

```json
{
  "document_id": 1,
  "title": "pointers.txt",
  "word_count": 4
}
```

ID зависит от уже сохранённых документов. Повторная загрузка создаёт новый документ.

Требования: ровно один multipart-файл `file`, расширение `.txt` без учёта ASCII-регистра, валидный UTF-8 и хотя бы один токен. Начальный UTF-8 BOM удаляется; U+0000 запрещён. Размер файла — до **5 MiB**, тела — до **6 MiB**. Название берётся из последнего компонента имени файла, до 255 байт.

### Поиск

```bash
curl --get \
  --data-urlencode 'q=умные указатели' \
  --data-urlencode 'limit=10' \
  http://127.0.0.1:8080/search
```

Пример ответа `200 OK` для коллекции из одного документа:

```json
{
  "results": [
    {
      "document_id": 1,
      "title": "pointers.txt",
      "score": 0.5753641449035618,
      "snippet": "Умные указатели управляют памятью."
    }
  ]
}
```

`q` обязателен, передаётся один раз, содержит хотя бы один токен и занимает не более 2048 байт после URL-декодирования. `limit` — целое от 1 до 100, по умолчанию 10; повтор параметра отвергается.

Если совпадений нет: `{"results": []}`. Score — оценка BM25, а не вероятность; добавление документов меняет статистику коллекции и может изменить оценки.

### Ошибки

```json
{
  "error": {
    "code": "InvalidQuery",
    "message": "Query must contain at least one word"
  }
}
```

| HTTP | Код |
|---|---|
| 400 | `InvalidRequest`, `InvalidText`, `InvalidQuery`, `InvalidLimit` |
| 413 | `DocumentTooLarge` |
| 415 | `UnsupportedFileType` |
| 500 | `InternalError` |

Для программной обработки используется `code`; `message` поясняет причину.

## Хранение и восстановление

Документы находятся в `data/documents/<id>.json`:

```json
{
  "schema_version": 1,
  "document_id": 1,
  "title": "pointers.txt",
  "text": "Умные указатели управляют памятью."
}
```

Запись сначала создаётся во временном файле, затем переименовывается. При восстановлении временные `.tmp` игнорируются.

При запуске `LoadAll()` читает документы, а `Restore()` строит новый индекс и заменяет текущий после успешного восстановления. Следующий ID — максимальный сохранённый ID плюс один, с проверкой переполнения. Повреждённые записи не пропускаются молча.

**Индекс находится в оперативной памяти и на диск не сохраняется.** После перезапуска он пересобирается из документов. При добавлении сначала сохраняется документ, затем обновляется индекс; при исключении индекса выполняется попытка удалить сохранённую запись.

Один каталог данных предназначен для одного процесса сервера.

## Проверки

### Ядро

В окружении с ICU, nlohmann_json и Catch2 3:

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DBUILD_SERVER=OFF \
  -DBUILD_TESTING=ON

cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
```

Проверки охватывают обработку текста, индекс, BM25, хранилище и движок. Отдельный исполняемый файл проверяет поведение индекса при ошибках выделения памяти.

### HTTP и клиент API

```bash
python3 tests/integration/http_smoke.py --binary build-server/local_search
node --test tests/web/api.test.mjs
```

Для тестов клиента нужен Node.js 20+. Он не требуется для работы самого сайта. HTTP smoke-тест запускается отдельно и не зарегистрирован в CTest.

## Ограничения v1

- NFC-нормализация и нижний регистр ICU с root locale.
- Буквы и цифры образуют токены; комбинируемые знаки сохраняются внутри слова.
- Морфологии, исправления опечаток и удаления стоп-слов нет: `указатель` и `указатели`, `е` и `ё` различаются.
- `C++` превращается в токен `c`.
- Фразового и семантического поиска пока нет.
- Сниппет показывает начало документа, без многоточий.
- Индекс должен помещаться в память; запуск требует обработки всей коллекции.
