# Local Search

Локальный поисковик по собственным текстовым документам на C++. Пользователь загружает `.txt`-файлы и получает лучшие документы по текстовому запросу. Ядро использует собственный инвертированный индекс и BM25.

**Статус:** v1 спроектирована, реализация в разработке. Этот README описывает целевой контракт первой версии. Команды сборки и запуска должны стать рабочими по мере выполнения [TASKS.md](TASKS.md); сейчас они не означают, что код уже написан или проверен. После реализации обновить статус и сверить команды с репозиторием.

## Возможности v1

- Загрузка одного `.txt`-документа в UTF-8 через `POST /documents`.
- Поиск через `GET /search` с ранжированием BM25 и ограничением количества результатов.
- Обработка русского и английского текста без учёта регистра.
- Возврат ID, названия, оценки и короткого отрывка документа.
- Сохранение документов на диске и восстановление индекса при запуске.
- Работа без внешней БД: индекс и статистика находятся в памяти.

Обязательная первая версия — backend, которым можно пользоваться через `curl`. Простая страница в браузере добавляется отдельной задачей после готовности API.

## Как работает поиск

При загрузке текст разбивается на нормализованные слова. Для каждого слова индекс хранит ID документов и число его упоминаний. В индексе также находятся длины документов и статистика коллекции.

При поиске запрос проходит ту же обработку. Движок читает списки его слов, накапливает оценки BM25, выбирает топ и загружает из хранилища названия и тексты выбранных документов. Исходные файлы всех документов для каждого запроса не перечитываются.

Запрос из нескольких слов допускает совпадение хотя бы одного слова. Вклад каждого уникального слова суммируется. Порядок слов и точное соседство в v1 не проверяются; повтор слова в запросе не увеличивает его вес.

## Стек

| Часть | Базовый вариант |
|---|---|
| Язык | C++20 |
| Сборка | CMake от 3.20, Ninja |
| HTTP-адаптер | cpp-httplib |
| JSON | nlohmann/json |
| UTF-8 и Unicode | ICU4C |
| Модульные тесты | Catch2 |
| HTTP-проверка | Python 3, стандартная библиотека |

HTTP-библиотека находится в слое обработчиков. Само ядро можно проверять без запущенного сервера. Если HTTP-слой реализуется на userver, задачи ядра и внешний API остаются теми же; команды запуска и зависимости нужно обновить под выбранный адаптер.

Версии cpp-httplib, nlohmann/json и Catch2 закрепляются в CMake при настройке репозитория. Первая конфигурация сборки может потребовать интернет для загрузки зависимостей.

## Сборка в Ubuntu или WSL2

Команды выполнять из корня репозитория. В Windows использовать терминал Ubuntu в WSL2. Базовые пакеты:

```bash
sudo apt update
sudo apt install build-essential cmake ninja-build libicu-dev git curl python3 pkg-config
```

Компилятор должен поддерживать C++20. ICU подключается как системная библиотека; остальные зависимости получает CMake согласно закреплённым версиям.

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build
ctest --test-dir build --output-on-failure
```

Целевые имена: `search_core` — библиотека ядра и хранилища, `local_search` — сервер, `search_tests` — C++-проверки. HTTP-проверка регистрируется в CTest после реализации API.

## Запуск

```bash
./build/local_search --host 127.0.0.1 --port 8080 --data-dir ./data
```

Параметры необязательны:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--host` | `127.0.0.1` | Адрес сервера |
| `--port` | `8080` | Порт, целое от 1 до 65535 |
| `--data-dir` | `./data` | Каталог сохранённых документов |
| `--help` | — | Справка |

Относительный каталог данных вычисляется от текущего рабочего каталога. Для повторного запуска нужно использовать тот же `--data-dir`. Один процесс сервера владеет одним каталогом данных.

Перед открытием порта сервер читает сохранённые записи и пересобирает индекс. Если окончательная запись повреждена, запуск завершается с ошибкой; документ не пропускается молча.

## Быстрый пример

Для примера сервер должен быть запущен с пустым каталогом данных. Создать файл без завершающего перевода строки:

```bash
printf '%s' 'Умные указатели управляют памятью.' > /tmp/pointers.txt
```

Загрузить:

```bash
curl -i -F 'file=@/tmp/pointers.txt;type=text/plain' http://127.0.0.1:8080/documents
```

Ожидаемый статус — `201 Created`. Тело ответа на пустой коллекции:

```json
{
  "document_id": 1,
  "title": "pointers.txt",
  "word_count": 4
}
```

Найти документ:

```bash
curl --get --data-urlencode 'q=умные указатели' --data-urlencode 'limit=10' http://127.0.0.1:8080/search
```

Ожидаемый статус — `200 OK`. Если в коллекции только этот документ, результат будет примерно таким; округление score может отличаться:

```json
{
  "results": [
    {
      "document_id": 1,
      "title": "pointers.txt",
      "score": 0.5753641449035618,
      "snippet": "Умные указатели управляют памятью."
    }
  ]
}
```

Загрузка других документов изменяет статистику BM25, поэтому может изменить оценки и порядок выдачи. Score не является вероятностью или процентом уверенности.

## HTTP API

### POST /documents

Принимает `multipart/form-data` с ровно одной частью-файлом `file`.

| Требование | Значение |
|---|---|
| Формат | `.txt`, расширение без учёта ASCII-регистра |
| Кодировка | Валидный UTF-8; начальный BOM допустим и удаляется |
| Размер файла | От 1 байта до 5 MiB включительно |
| Лимит HTTP-тела | 6 MiB вместе с multipart-разметкой |
| Содержимое | Как минимум один токен; U+0000 запрещён |
| Название | Последний компонент имени, непустой UTF-8 без U+0000, до 255 байт |

MIME части не заменяет проверку текста. Имена файлов служат названиями для отображения; пути хранения формируются по серверным ID. Лишние части multipart отвергаются.

После успешного ответа документ уже сохранён и проиндексирован. Повторная загрузка того же текста или имени создаёт отдельный документ с новым ID.

Ответ `201` содержит `document_id`, `title`, `word_count`.

### GET /search

| Параметр | Правило |
|---|---|
| `q` | Обязательный, один; до 2048 байт после URL-декодирования, валидный текст с хотя бы одним токеном |
| `limit` | Необязательный, один; десятичное целое от 1 до 100, по умолчанию 10 |

Ответ `200`:

```json
{"results": []}
```

При наличии результатов каждый объект содержит:

| Поле | Содержимое |
|---|---|
| `document_id` | Положительный ID документа |
| `title` | Название |
| `score` | Суммарная оценка BM25 для этого запроса |
| `snippet` | Первые максимум 200 Unicode code points исходного текста, без многоточия |

Порядок — score по убыванию, при равенстве ID по возрастанию. Отсутствие совпадений возвращает `200` и пустой массив.

### Ошибки

Все ответы этих маршрутов имеют JSON Content-Type. Формат ошибки:

```json
{
  "error": {
    "code": "InvalidQuery",
    "message": "Query must contain at least one word"
  }
}
```

Текст `message` может уточнять причину. Для программной обработки использовать `code`.

| HTTP | Код | Причина |
|---:|---|---|
| 400 | `InvalidRequest` | Некорректный multipart, нет файла, лишние части, неверное название |
| 400 | `InvalidText` | Пустой документ, нет токенов, неверный UTF-8 или U+0000 |
| 400 | `InvalidQuery` | Нет `q`, повтор `q`, неверный текст, нет токенов или превышен лимит |
| 400 | `InvalidLimit` | Неверное значение или повтор `limit` |
| 413 | `DocumentTooLarge` | Превышен лимит файла или тела |
| 415 | `UnsupportedFileType` | Расширение отличается от `.txt` |
| 500 | `InternalError` | Ошибка хранилища или внутренняя ошибка |

## Хранение и согласованность

Один документ хранится в `data/documents/<id>.json` вместе с метаданными:

```json
{
  "schema_version": 1,
  "document_id": 1,
  "title": "pointers.txt",
  "text": "Умные указатели управляют памятью."
}
```

JSON — внутренний формат хранения; пользователь загружает `.txt`. Новая запись сначала записывается во временный файл в том же каталоге, затем переименовывается в окончательный. Временные `.tmp`-файлы при восстановлении игнорируются.

Длины документов и статистика вычисляются заново из токенов при запуске. Индекс на диск не сохраняется. Следующий ID выбирается больше максимального сохранённого.

Для v1 операции движка защищены одним mutex. При добавлении сначала готовится копия индекса, затем сохраняется запись и публикуется готовое состояние. Это простой способ сохранить согласованность при ошибке подготовки или записи для небольшой коллекции. Копирование занимает время и дополнительную память; оптимизация добавления относится к следующему этапу.

## Правила текста и ограничения

- Используется NFC-нормализация и нижний регистр с root locale. Сохранённый исходный текст сохраняет исходный регистр.
- Токены состоят из Unicode-букв и десятичных цифр; комбинируемые знаки допускаются внутри слова. Остальные символы разделяют слова.
- `указатель` и `указатели`, а также `е` и `ё` — разные токены.
- Стоп-слова не удаляются. `C++` индексируется как `c`.
- Точные фразы, исправление опечаток, морфология и семантическое сходство в v1 не реализуются.
- Отрывок — начало документа; поиск наиболее подходящего фрагмента добавляется позже.
- При запуске все документы обрабатываются заново; индекс должен помещаться в память.
- Один каталог данных используется одним процессом. Записи не следует редактировать вручную во время работы сервера.

## Проверка и дальнейшие этапы

Задачи и критерии приёмки находятся в [TASKS.md](TASKS.md). Готовность v1 подтверждается сборкой, тестами и цепочкой: загрузка → поиск → перезапуск → повторный поиск с тем же ID.

После завершения backend можно добавить страницу, отрывки вокруг совпадений, удаление документов, сохранение индекса и измерения скорости. Векторный и гибридный поиск — отдельный следующий этап.
