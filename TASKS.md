# Local Search — задачи для v1

Этот файл можно положить в корень репозитория как `TASKS.md`. Каждая задача ниже подходит для отдельного issue или небольшого merge request. Реализации в этом документе нет: он фиксирует поведение, интерфейсы и критерии готовности.

## Объём первой версии

- Один C++ backend, работающий локально на `127.0.0.1:8080`.
- `POST /documents`: загрузка одного `.txt`-документа в UTF-8 и синхронная индексация.
- `GET /search?q=…&limit=10`: поиск через собственный инвертированный индекс и BM25.
- Документы сохраняются на диске; индекс находится в памяти и восстанавливается при запуске.
- Проверять backend можно через `curl`. Фронт — отдельная необязательная задача после готовности backend.

В этой версии запрос из нескольких слов имеет OR-семантику: достаточно совпадения одного слова. Порядок слов и соседство не проверяются. Повтор одного слова в запросе не увеличивает его вес. Стемминг, лемматизация, стоп-слова, векторный поиск, удаление документов и авторизация относятся к следующим версиям.

## Решения, общие для всех задач

| Параметр | Контракт v1 |
|---|---|
| Язык | C++20, namespace `local_search` |
| Рабочая среда | Linux или Ubuntu в WSL2 |
| Сборка | CMake от 3.20, Ninja |
| HTTP | Базовый вариант: `cpp-httplib`; библиотека используется только в HTTP-слое |
| JSON | `nlohmann/json`; JSON появляется в HTTP и файловом хранилище |
| Unicode | ICU4C для проверки UTF-8, нормализации и обработки регистра |
| Тесты | Catch2 для C++; Python 3 из стандартной библиотеки для HTTP-проверки |
| Лимит файла | 5 MiB = 5 × 1024 × 1024 байт; проверяется до удаления BOM |
| Лимит HTTP-тела | 6 MiB, включая multipart-разметку |
| Лимит запроса | 2048 байт после URL-декодирования |
| `limit` | Целое число от 1 до 100, по умолчанию 10 |
| BM25 | `k1 = 1.2`, `b = 0.75`, положительный IDF из TASK-04 |
| ID | Положительный `std::uint64_t`, первый ID — 1 |
| Одинаковая оценка | Сначала меньший `document_id` |
| Отрывок | Первые максимум 200 Unicode code points исходного текста; без многоточия |
| Параллельные запросы | HTTP может принимать их параллельно; операции одного `SearchEngine` защищены общим mutex |

Зависимости нужно закрепить на конкретных релизах или commit hash в TASK-00. API `cpp-httplib` может различаться между версиями: сверять примеры с выбранным релизом. Если решишь использовать знакомый userver, заменить HTTP-адаптер и запуск сервера; контракты поиска и API сохранить.

## TASK-01 — определить Document и SearchResult

**Цель:** согласовать типы, которыми пользуются остальные модули.

**Файлы:** `src/search/document.hpp`, `src/search/search_result.hpp`, `src/search/errors.hpp`.

**Контракт типов:**

```cpp
using DocumentId = std::uint64_t;

struct Document {
    DocumentId id;
    std::string title;
    std::string text;
};

struct SearchResult {
    DocumentId document_id;
    std::string title;
    double score;
    std::string snippet;
};
```

Объявления размещать в namespace `local_search`, добавить необходимые стандартные include. Строки владеют памятью. В `Document.text` хранится исходный текст после удаления необязательного начального UTF-8 BOM; индексная нормализация не меняет сохранённый текст.

Уточнение прежнего эскиза: `word_count` не дублируется в `Document`. Длина документа вычисляется из токенов и хранится в `InvertedIndex`; в POST-ответ её передаём отдельно.

**Что сделать:**

- [ ] Определить указанные типы.
- [ ] Определить `ValidationError` с машинным кодом и сообщением, а также `StorageError` для ошибок сохранения/чтения.
- [ ] Не хранить в типах HTTP status, JSON-объекты или ссылки на запрос.
- [ ] Значения ID, длины и BM25 создавать в соответствующих модулях, а не в конструкторах DTO.

**Готово, когда:** все модули могут подключить эти заголовки без HTTP-библиотеки; результаты не содержат `string_view`, указывающих в уничтоженный запрос. Отдельные тесты простых структур не нужны.

## TASK-02 — реализовать TextProcessor

**Цель:** одинаково превращать документы и запросы в токены.

**Файлы:** `src/search/text_processor.hpp/.cpp`, `tests/unit/text_processor_test.cpp`.

**Интерфейс:**

```cpp
class TextProcessor {
public:
    std::vector<std::string> Process(std::string_view text) const;
};
```

**Правила v1:**

1. Строго проверить UTF-8. Ошибочные последовательности не заменять молча на символ замены.
2. Игнорировать UTF-8 BOM только в начале входа. Символ U+0000 считать недопустимым текстом.
3. Нормализовать в NFC, привести строку к нижнему регистру с root locale, снова привести к NFC.
4. Слово — последовательность Unicode-букв и десятичных цифр. Комбинируемые знаки разрешены внутри уже начавшегося слова. Остальные символы разделяют слова.
5. Сохранить порядок и повторы токенов. Вернуть собственные строки UTF-8.

Для русского и английского текста этого достаточно для v1. `е` и `ё` различаются; морфологические формы не объединяются. Например, `C++` превращается в `c`, `hello_world` — в два слова. Это часть согласованного поведения.

**Что сделать:**

- [ ] Использовать ICU для Unicode-преобразований; побайтовый `std::tolower` не подходит для кириллицы.
- [ ] Реализовать обработку пустого входа: пустой вектор.
- [ ] Для валидного текста только с разделителями вернуть пустой вектор. Решение, допустим ли он для документа или запроса, принимает `SearchEngine`.
- [ ] Некорректный UTF-8 и U+0000 оформить как ошибку валидации; внешний модуль уточнит её код для документа или запроса.

**Проверки:**

- [ ] `"Умные указатели, указатели!"` → `{"умные", "указатели", "указатели"}`.
- [ ] Разный регистр даёт одинаковые токены.
- [ ] Пробелы, CRLF, табуляция и пунктуация не дают пустых токенов.
- [ ] Канонически эквивалентные Unicode-формы дают одинаковый результат.
- [ ] `ЁЖ` → `ёж`; `еж` остаётся отдельным словом.
- [ ] Начальный BOM не входит в первый токен; некорректный UTF-8 отвергается.

**Готово, когда:** один экземпляр этого модуля подходит и для индексирования, и для поиска; сохранённый исходный текст не переписывается в нижнем регистре.

## TASK-03 — реализовать InvertedIndex

**Цель:** по слову быстро получать документы, частоты и статистику для BM25.

**Файлы:** `src/search/inverted_index.hpp/.cpp`, `tests/unit/inverted_index_test.cpp`.

**Представление:**

```cpp
struct Posting {
    DocumentId document_id;
    std::size_t frequency;
};

// Приватные поля InvertedIndex:
std::unordered_map<std::string, std::vector<Posting>> postings_;
std::unordered_map<DocumentId, std::size_t> document_lengths_;
std::size_t total_word_count_ = 0;
```

**Интерфейс:**

```cpp

const std::vector<Posting>* Find(std::string_view word) const;
std::size_t GetDocumentLength(DocumentId id) const;
std::size_t DocumentCount() const;
double AverageDocumentLength() const;
void Swap(InvertedIndex& other) noexcept;
```

**Алгоритм добавления:** проверить ID и непустой список → построить локальные частоты слов → добавить по одной записи на уникальное слово → записать длину → обновить суммарную длину.

**Что сделать:**

- [ ] Отвергать ID 0, повторное добавление того же ID и пустой список токенов. Проверять до изменения состояния.
- [ ] Считать `N` как размер `document_lengths_`, `df` как размер соответствующего postings list.
- [ ] `Find()` для неизвестного слова возвращает `nullptr` и не создаёт запись через `operator[]`.
- [ ] Для пустого индекса `AverageDocumentLength()` возвращает `0.0`; для непустого использовать вещественное деление.
- [ ] Реализовать копирование индекса стандартными контейнерами и `Swap()` без выделения памяти: это используется в TASK-06.
- [ ] Не возвращать изменяемые списки наружу. Ссылки и указатели на postings используются только пока состояние защищено mutex движка.

**Проверки:**

- [ ] Токены `{"кот", "кот", "дом"}` дают одну запись слова `кот` с `tf=2`, одну запись `дом` с `tf=1`, длину 3.
- [ ] После второго документа со словом `кот` значение `df` равно 2, а не сумме всех упоминаний.
- [ ] Неизвестное слово не меняет статистику.
- [ ] Повторный ID не изменяет индекс.
- [ ] Копия индекса независима от оригинала; `Swap()` переносит postings, длины и суммарную длину вместе.

**Готово, когда:** для любого найденного posting можно получить все числа для BM25 без чтения документа с диска.

## TASK-04 — реализовать BM25

**Цель:** вычислять вклад одного слова запроса в оценку одного документа.

**Файлы:** `src/search/bm25.hpp/.cpp`, `tests/unit/bm25_test.cpp`.

**Интерфейс:**

```cpp
double Bm25Contribution(
    std::size_t tf, std::size_t df, std::size_t document_count,
    std::size_t document_length, double average_document_length,
    double k1 = 1.2, double b = 0.75
);
```

**Формула v1:**

\[
\operatorname{IDF}(t)=\ln\left(1+\frac{N-df(t)+0.5}{df(t)+0.5}\right),
\]

\[
\operatorname{contribution}(t,d)=\operatorname{IDF}(t)
\frac{tf(t,d)(k_1+1)}{tf(t,d)+k_1\left(1-b+b\frac{|d|}{avgdl}\right)}.
\]

Суммарная оценка — сумма вкладов уникальных слов запроса. Положительная форма IDF позволяет учитывать даже слово, встречающееся во всех документах.

**Что сделать:**

- [ ] Использовать `double` и натуральный логарифм; преобразовать счётчики в `double` до дробных операций. Для IDF удобно `std::log1p`.
- [ ] При `tf=0` вернуть 0.
- [ ] Для остальных входов проверять `N>0`, `1<=df<=N`, `0<tf<=document_length`, `avgdl>0` и конечность `avgdl`.
- [ ] Для параметров проверять конечность, `k1>0` и `0<=b<=1`. Некорректные входы считать ошибкой программирования, например `std::invalid_argument`.
- [ ] Сохранить функцию чистой: без файлов, HTTP и изменения индекса.

**Проверки:**

- [ ] Для `N=3`, `df=2`, `tf=2`, `document_length=4`, `avgdl=3`, `k1=1.2`, `b=0.75` результат примерно `0.5908617053374962` с допуском `1e-9`.
- [ ] При одинаковых остальных параметрах более редкое слово даёт больший вклад.
- [ ] Увеличение частоты даёт рост с насыщением, а не линейный рост.
- [ ] При одинаковой частоте и `b>0` более длинный документ получает меньший вклад.
- [ ] При `df=N` вклад положителен; при `tf=0` равен нулю.

**Готово, когда:** функция проходит численный пример и проверки свойств. Не требуется воспроизводить бит в бит оценки готового поискового сервера.

## TASK-05 — реализовать DocumentStore

**Цель:** сохранять документ с метаданными и читать его после перезапуска.

**Файлы:** `src/storage/document_store.hpp/.cpp`, `tests/unit/document_store_test.cpp`.

**Интерфейс:**

```cpp
explicit DocumentStore(std::filesystem::path data_dir);
void Save(const Document& document);
Document Get(DocumentId id) const;
std::vector<Document> LoadAll() const;
```

**Формат хранения:** один JSON-record на документ: `data/documents/<id>.json`.

```json
{
  "schema_version": 1,
  "document_id": 42,
  "title": "pointers.txt",
  "text": "Умные указатели управляют памятью."
}
```

Загружаемый формат остаётся `.txt`. JSON — внутреннее представление исходного текста и метаданных в одном файле. Так не потребуется отдельно синхронизировать TXT и общий manifest. Индекс, длины и BM25 score на диск не записываются.

**Что сделать:**

- [ ] Создавать каталог `documents` внутри заданного `data_dir`.
- [ ] Формировать путь только из серверного ID; клиентское название используется только как `title`.
- [ ] Сериализовать запись, записать временный файл `<id>.json.tmp` в том же каталоге, проверить запись/flush/close и переименовать в `<id>.json`.
- [ ] Не перезаписывать существующий ID. После успешного rename не выполнять дополнительных действий, способных превратить успех в исключение.
- [ ] При ошибке возвращать `StorageError`; временный файл по возможности удалять без нового исключения.
- [ ] В `LoadAll()` читать только окончательные `.json`-записи. `.tmp` не индексировать.
- [ ] Проверять schema version, положительный ID, типы полей и совпадение ID с именем файла. Вернуть документы по возрастанию ID.
- [ ] Повреждённую окончательную запись считать ошибкой восстановления; не скрывать её молчаливым пропуском.

**Проверки:**

- [ ] Сохранить/прочитать документ: ID, название и текст совпадают, включая кириллицу, кавычки и переносы строк.
- [ ] Новый экземпляр хранилища читает ранее сохранённый документ.
- [ ] Два документа с одинаковым названием хранятся независимо.
- [ ] Временный файл игнорируется при загрузке; повреждённый `.json` вызывает ошибку.
- [ ] Ошибка записи не создаёт окончательную запись; неизвестный ID и повторное сохранение существующего ID вызывают ошибку.

**Готово, когда:** обычный перезапуск сохраняет документы и их ID. Один процесс владеет каталогом данных; поддержка нескольких серверов с общим каталогом не входит в v1.

## TASK-06 — реализовать SearchEngine

**Цель:** связать обработку текста, индекс, BM25 и хранилище.

**Файлы:** `src/search/search_engine.hpp/.cpp`, `tests/unit/search_engine_test.cpp`.

**Интерфейс:**

```cpp
struct AddedDocument {
    DocumentId document_id;
    std::string title;
    std::size_t word_count;
};

explicit SearchEngine(DocumentStore& store);
void Restore();
AddedDocument AddDocument(std::string title, std::string text);
std::vector<SearchResult> Search(std::string_view query, std::size_t limit) const;
```

`AddedDocument` разместить в `search_engine.hpp`. Хранилище должно жить дольше движка; в `main` создать его первым. Движок владеет `TextProcessor`, `InvertedIndex`, `next_id_` и mutex. `Search()` использует `mutable` mutex для защиты чтения общего состояния; результаты возвращаются по значению.

**Добавление:**

- [ ] Проверить размер текста, UTF-8, U+0000, название; убрать начальный BOM и выполнить `Process()`.
- [ ] Отвергнуть документ без токенов. При неверном тексте использовать код `InvalidText`.
- [ ] Под общим mutex выбрать следующий ID. Повторная загрузка такого же текста создаёт новый документ; дедупликации в v1 нет.
- [ ] Подготовить новый индекс в локальной копии: скопировать текущий, добавить туда документ.
- [ ] До сохранения подготовить и данные `AddedDocument`, включая принадлежащее ему название, чтобы после фиксации не копировать строки с возможным выделением памяти.
- [ ] Только после успешной подготовки сохранить документ через `DocumentStore::Save()`.
- [ ] После успешного сохранения опубликовать индекс через `Swap()` без исключений, обновить `next_id_`, вернуть `AddedDocument`.

Копирование индекса при добавлении — осознанное упрощение для небольшой коллекции: ошибка подготовки или записи не оставляет частично добавленный документ в работающем индексе. Это стоит времени и дополнительной памяти; оптимизацию можно делать после измерений. Переполнение ID проверять до сохранения.

**Поиск:**

- [ ] Проверить длину/UTF-8 запроса, `limit`, выполнить `Process()`; запрос без токенов отвергнуть как `InvalidQuery`.
- [ ] Удалить повторы слов только в запросе, не в документах.

## TASK-08 — реализовать POST /documents

**Цель:** принять файл, проверить запрос и вызвать движок.

**Файлы:** `src/http/upload_handler.hpp/.cpp`, `src/http/api_error.hpp/.cpp`.

**Вход:** `multipart/form-data`, ровно одна часть-файл с именем `file`. Имя файла имеет расширение `.txt` без учёта ASCII-регистра. Остальные файлы/поля в этом контракте отвергаются. MIME части не заменяет проверку содержимого UTF-8.

**Что сделать:**

- [ ] Извлечь файл штатным multipart parser выбранной HTTP-библиотеки.
- [ ] Проверить наличие одной части `file`, название и расширение.
- [ ] Для отображаемого названия оставить последний компонент после `/` или `\\`; не использовать клиентское название в пути хранения. Название должно быть непустым UTF-8 без U+0000, максимум 255 байт.
- [ ] Проверить размер: до 5 MiB включительно. Нулевой размер — ошибка текста.
- [ ] Передать название и содержимое в `SearchEngine::AddDocument()`; не считать частоты в обработчике.
- [ ] После успешного сохранения и индексации вернуть `201` и JSON с `document_id`, `title`, `word_count`.
- [ ] Ошибки валидации отобразить по таблице ниже. Неожиданные исключения вернуть как `500 InternalError`.
- [ ] Перехватить отказ библиотеки по лимиту тела и привести его к JSON-ошибке `413 DocumentTooLarge`.

**Успешный ответ:**

```json
{"document_id": 1, "title": "pointers.txt", "word_count": 4}
```

**Единый формат ошибок:**

```json
{"error": {"code": "InvalidText", "message": "Document must contain at least one word"}}
```

| Ситуация | HTTP | `error.code` |
|---|---:|---|
| Некорректный multipart, нет файла, лишние части, неверное название | 400 | `InvalidRequest` |
| Не `.txt` | 415 | `UnsupportedFileType` |
| Файл больше 5 MiB или тело больше 6 MiB | 413 | `DocumentTooLarge` |
| Пустой текст, нет слов, неверный UTF-8, U+0000 | 400 | `InvalidText` |
| Ошибка хранилища/подготовки индекса | 500 | `InternalError` |

**Готово, когда:** запрос через `curl -F` возвращает ID, а следующий GET сразу находит документ. POST, отвергнутый при валидации или до фиксации добавления, не меняет работающий индекс. Все ответы маршрута имеют JSON Content-Type. Ошибка передачи ответа после фиксации не отменяет уже добавленный документ.
